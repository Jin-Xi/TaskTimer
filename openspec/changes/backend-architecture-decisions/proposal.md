# 后端架构决策记录

## 变更概述

记录 ChronoFlow 前后端分离改造的核心架构决策。

## 决策日期

2026-03-18

## 核心决策

### 1. 登录方式

**决策：用户名 + 密码**

- ✅ 采用：用户名 + 密码登录
- ❌ 暂不实现：第三方登录（Google、GitHub、微信等）

**理由：**
- 简化初期开发复杂度
- 降低对第三方服务的依赖
- 用户名比邮箱更灵活（部分用户可能不想暴露邮箱）

**密码要求：**
- 最少 6 位字符
- 使用 bcrypt 哈希存储

---

### 2. 数据迁移策略

**决策：默认数据写入数据库**

- 新用户注册时，系统自动初始化默认分类数据
- 默认分类与现有 localStorage 版本保持一致

**默认分类：**
| 名称 | 颜色 |
|------|------|
| chronoflow | green |
| ochre | ochre |
| terracotta | terracotta |
| slate-river | slate-river |

---

### 3. 双模式架构

**决策：登录界面可选择"单机使用"**

系统支持两种使用模式：

| 模式 | 入口 | 数据存储 | AI 配置 |
|------|------|----------|---------|
| **单机模式** | 点击"单机使用"按钮 | localStorage | 用户自行配置 API Key |
| **云端模式** | 输入用户名密码登录 | MySQL 数据库 | 后台统一配置 |

**模式切换流程：**
```
启动应用 → 显示登录界面
              ├── 点击"单机使用" → 进入本地模式
              └── 输入用户名密码登录 → 进入云端模式
```

---

### 4. 后端框架

**决策：FastAPI (Python) + MySQL**

| 组件 | 技术选型 |
|------|----------|
| 后端框架 | FastAPI (Python 3.11+) |
| 数据库 | MySQL 8.0+ |
| ORM | SQLAlchemy 2.0 |
| 认证 | JWT |
| 部署 | Docker Compose |

**理由：**
- FastAPI 高性能异步支持
- Python 生态丰富，便于 AI 集成
- MySQL 成熟稳定，适合生产环境

---

### 5. API Key 管理策略

**决策：按模式差异化处理**

| 模式 | API Key 来源 | 配置方式 |
|------|-------------|----------|
| 单机模式 | 用户自行配置 | 前端 AISettingsModal，存储在 localStorage |
| 云端模式 | 后台统一管理 | 后端环境变量，用户无需关心 |

**后端 AI 配置（云端模式）：**
```bash
# backend/.env
AI_PROVIDER=deepseek  # 或 openai、google
AI_API_KEY=sk-xxxxx
AI_MODEL=deepseek-chat
```

---

### 6. 多设备实时同步

**决策：暂不实现，作为后期规划**

| 功能 | 当前版本 | 后期规划 |
|------|----------|----------|
| RESTful API | ✅ 实现 | - |
| 数据导入导出 | ✅ 实现 | - |
| WebSocket 多设备实时同步 | ❌ 暂不实现 | 🔮 后期规划 |

**当前替代方案：**
- 手动刷新获取最新数据
- 页面切换时自动重新获取

## 影响范围

### 前端影响
- 登录页面需添加"单机使用"按钮
- 需实现 `useAppMode` Hook 管理模式状态
- AI 设置页面根据模式显示/隐藏 API Key 配置

### 后端影响
- 用户表使用 `username` 为主（无需 email）
- 注册时自动初始化默认分类
- 需实现 AI 代理端点（云端模式）

### 数据库影响
- 用户表结构简化（移除 email 必填）
- 新增默认分类初始化逻辑
